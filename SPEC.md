# Libretto

Spec-driven end-to-end testing for TypeScript. You write the app's behavior in plain markdown. Libretto turns it into Playwright tests, runs them, and when one fails, tells you whether the app or the test is broken.

## Workflow

```
specs/*.md ──generate──▶ .libretto/generated/*.spec.ts ──run──▶ results
                                                                  │ failure, then you decide
                                                                  ▼
                                   triage (manual) ──▶ verdict: app-broken | test-broken
                                                                  │ test-broken
                                                                  ▼
                                            fix ──▶ patch to spec, then regenerate
```

Four commands, each usable alone. Nothing spends AI tokens unless you invoke `generate`, `triage`, or `fix`.

| Command | Does |
| --- | --- |
| `libretto generate [spec...]` | Agent explores the app through Playwright MCP and writes Playwright Test code for each stale spec. |
| `libretto run [spec...]` | Wraps `@playwright/test`. Runs generated tests and records failures in `.libretto/last-run.json`. Never calls AI, never edits files. |
| `libretto triage [spec...]` | Run by hand after a failed `run`. For each recorded failure, an agent inspects the trace, screenshots, DOM snapshot, and probes the live app. Writes verdicts to `.libretto/triage.json`. |
| `libretto fix [spec...]` | Reads the triage verdicts, proposes repairs for `test-broken` failures, asks before applying. |

## Decisions made

- **Output is generated Playwright Test code**, committed to git. Runs are deterministic and cost nothing in AI calls. AI is used only in `generate`, triage, and `fix`.
- **`run` wraps `@playwright/test`.** We inherit parallelism, traces, reporters, fixtures, and `playwright.config`. We add the spec-to-test mapping and triage.
- **Specs are markdown with light conventions** (see below).
- **Staleness is hash-tracked.** Each generated file records a hash of its source spec. `generate` regenerates only stale files. `run` warns when a spec changed but its test did not.
- **Failure flow is three manual steps.** `run` reports, `triage` diagnoses, `fix` repairs. Each is a separate command so tokens are only spent when you ask.
- **Shared context is an app spec plus env placeholders.** Secrets never reach the agent or git.
- **AI backend is pluggable, with Claude and GitHub Copilot both supported in v1.**
- **Packaging:** npm package with a `libretto` CLI bin, a programmatic API, and `libretto.config.ts`.

## Project layout (user's repo)

```
libretto.config.ts
specs/
  app.md                  # describes the app; fed to every generation
  fixtures/logged-in.md   # reusable setup, referenced by scenarios
  auth/login.md
.libretto/
  generated/              # machine-written, do not edit
    auth/login.generated.spec.ts
  last-run.json           # verdicts consumed by `fix`
```

Generated files carry a header:

```ts
// GENERATED by libretto from specs/auth/login.md (hash: 9f2c1a…)
// DO NOT EDIT. Edit the spec and run `libretto generate`.
```

The `.libretto/generated/` name and `.generated.spec.ts` suffix signal ownership. See open question 1.

## Spec format

```md
---
tags: [smoke]
uses: [logged-in]        # fixture specs run first
---
# Login

## Scenario: valid credentials
Steps:
- Open the login page
- Enter username `alice` and password {{env.ALICE_PASSWORD}}
- Click "Log in"

Expect:
- The text "Welcome, alice" is visible
```

- Prose is interpreted by the agent. Only `Steps` and `Expect` headings are structural, so a failure maps to a specific step.
- `{{env.NAME}}` is emitted as `process.env.NAME` in generated code. The agent never sees the value. During generation the runner supplies it to the browser out of band.
- `app.md` holds base URL, page map, naming conventions, and anything the agent can't discover from the UI.

## Components

```ts
interface AgentRunner {
  // Starts an agent session with Playwright MCP attached and returns when it finishes.
  run(task: AgentTask): Promise<AgentResult>
}
```

- `AgentRunner` is the only AI seam. Implementations: `ClaudeRunner`, `CopilotRunner`.
- `SpecParser`: markdown to `Spec { scenarios: Scenario[], uses, tags, hash }`.
- `Generator`: spec + `app.md` + fixtures to a generated `.spec.ts`, using an `AgentRunner`.
- `Runner`: invokes Playwright Test, collects results into `RunResult`.
- `Triager`: failed test + trace + screenshot + DOM snapshot + spec to `Verdict`. The agent also gets Playwright MCP to probe the live app.
- `Fixer`: `Verdict` to a patch for the spec or the generated test.

```ts
type Verdict =
  | { kind: 'app-broken'; evidence: string }
  | { kind: 'test-broken'; evidence: string; cause: 'spec-wrong' | 'generated-code-wrong' }
  | { kind: 'inconclusive'; evidence: string }
```

`generated-code-wrong` is fixed by regenerating. `spec-wrong` means the spec no longer matches the app, so the fix patches the markdown and then regenerates. Neither edits a generated file by hand.

## Decisions (round 2)

- Generated naming: `.libretto/generated/` and `*.generated.spec.ts`, committed.
- Triage gets everything: trace, screenshots, DOM snapshot, and live probing of the app through Playwright MCP.
- The user starts the app under test. There is no `webServer` option. Triage probes the `baseURL` from config and, if it is unreachable, falls back to recorded artifacts and says so in the verdict.
- Triage is a manual command, never automatic, and runs after Playwright's own retries have already finished because it reads `last-run.json`.
- `fix` patches the spec when the app legitimately changed, then regenerates.
- Playwright `storageState` is supported, so fixtures like `logged-in` run once per suite.
- Hand-edited generated files are overwritten by `generate`, with a warning that names the file.
- `uses:` fixtures can chain. Cycles are rejected at parse time.
- Tooling: pnpm, TypeScript, vitest, ESM only.

## Agent backends: what each SDK supports

Both ship an in-process TypeScript SDK, so we do not need to shell out to CLIs. Details below come from the vendors' docs as of today. Treat the Copilot MCP surface as the least certain, since its docs call MCP "evolving".

| Need | Claude (`@anthropic-ai/claude-agent-sdk`) | Copilot (`@github/copilot-sdk`) |
| --- | --- | --- |
| Run an agent | `query({ prompt, options })`, async generator of messages | `client.createSession()`, then `session.sendAndWait()` or `send()` plus `session.on()` events |
| Attach Playwright MCP | `mcpServers: { playwright: { command, args } }` (stdio, SSE, HTTP, or in-process) | `mcpServers: { playwright: { type: 'local', command, args, tools: ['*'] } }` |
| Our own tools (for example, read the spec, write the test) | In-process MCP via `tool()` and `createSdkMcpServer()` | `defineTool()` with Zod |
| Tool permissions | `allowedTools`, `disallowedTools`, `canUseTool`, `permissionMode` | `onPermissionRequest` handler. `approveAll` throws if managed settings are enabled |
| Tool naming | `mcp__<server>__<tool>` | `<server>-<tool>` |
| Structured output (for `Verdict`) | `outputFormat: { type: 'json_schema' }` | `responseSchema` with a Zod schema. Marked preview, and some gateways ignore it |
| Working dir, model, prompt | `cwd`, `model`, `systemPrompt` | `workingDirectory`, `model`, `systemMessage` |
| Cancel | `abortController` | `session.abort()` |
| Limits | `maxTurns`, `maxBudgetUsd` | none found |
| Auth | Env vars passed to the CLI subprocess | Copilot CLI login or `COPILOT_GITHUB_TOKEN`/`GH_TOKEN`. BYOK also works |

Implications for the design:

- **No custom MCP is needed.** Playwright's own MCP server attaches to both as stdio. (Fallback, if its `--secrets` option does not cover secret typing in the spike: a stdio shim inside the agent module. See docs/ARCHITECTURE.md.)
- **Tool names are abstracted at one seam: the agent gets no built-in tools.** Built-ins (file edit, shell) are where Claude and Copilot differ most. Instead the agent receives only Playwright MCP plus a handful of Libretto tools defined once, vendor-neutrally:

  ```ts
  interface LibrettoTool<I> {
    name: string                 // 'write_test', 'submit_verdict', ...
    description: string
    input: z.ZodType<I>
    handler(input: I): Promise<string>
  }
  ```

  `ClaudeRunner` wraps these with `tool()` and `createSdkMcpServer()`. `CopilotRunner` wraps them with `defineTool()`. Each runner also turns off its built-ins (`tools: []` on Claude, `availableTools` on Copilot) and handles its own name prefix. Nothing outside the runner sees `mcp__x__y` or `x-y`.
- **The permission policy becomes trivial.** Allow what we attached, deny everything else. There is no path-glob policy to translate between `canUseTool` and `onPermissionRequest`. Path restrictions live inside our own `write_test` handler, which can refuse any path outside `.libretto/generated/` and `specs/`.
- **`submit_verdict` replaces structured output.** The verdict is a tool call validated by Zod in our handler. That works the same on both vendors and avoids Copilot's preview `responseSchema`. If the agent never calls it, that is an `inconclusive` verdict.
- **What stays vendor-specific, inside the runner:** the run loop, event streaming into our logger, auth, and cancellation.
- **Do not go further.** We do not abstract Playwright MCP's own tool names (`browser_click` and the like). They are identical on both backends and the agent sees them directly.
- **Secrets:** the agent types `{{env.X}}` placeholders; Playwright MCP's `--secrets <dotenv>` substitutes them by name in `browser_type` and `browser_fill_form`. The dotenv is written 0600 under `.libretto/` for the session and deleted after. Values never enter a prompt, a log, or git.

## Models and cost

Decided with pay-per-token API keys in mind.

- **Model names are vendor strings passed through.** `model: 'claude-opus-5-5'` or `'gpt-5'`. No tier mapping to maintain.
- **One default, per-command override.** Zero config to start, tune only where it hurts.
- **Where quality is worth the tokens:** `generate` first, since its output is committed and reused on every run, and brittle selectors repeat forever. `triage` second, since a wrong verdict sends you the wrong way. `fix` least, because it ends in another `generate` which catches a bad patch.
- **Budget caps per command.** `maxTurns` and `maxBudgetUsd` in config. Claude's SDK enforces both natively. Copilot has no budget option, so `CopilotRunner` counts turns itself and aborts the session when the cap is hit. Hitting a cap during triage yields an `inconclusive` verdict with `evidence: 'budget exhausted'`.

```ts
// libretto.config.ts
export default defineConfig({
  baseURL: 'http://localhost:3000',
  specs: 'specs',
  agent: {
    backend: 'claude',           // 'claude' | 'copilot'
    model: 'claude-sonnet-5-5',  // default for every command
    maxTurns: 40,
    maxBudgetUsd: 2,
  },
  generate: { model: 'claude-opus-5-5', maxBudgetUsd: 5 },
  triage:   { model: 'claude-opus-5-5' },
  fix:      {},                   // inherits agent.*
})
```
